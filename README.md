# Лабораторная работа №10
## Блокирующие вызовы сокетов и состояние TIME_WAIT

**Цель работы:** изучить блокирующие вызовы accept() и recv(), состояние TIME_WAIT и флаг SO_REUSEADDR.

**Среда:** Windows, Python 3.

## Файлы

- socket_server.py — блокирующий TCP-сервер на 127.0.0.1:9999.
- socket_client.py — клиент с паузами перед подключением и отправкой данных.

В опубликованном сервере строка SO_REUSEADDR раскомментирована согласно последнему пункту задания.

## Запуск

В первом окне cmd:

    python socket_server.py

Во втором окне cmd:

    python socket_client.py

## Результаты эксперимента

При ожидании подключения внутри accept() Диспетчер задач показывал 0% CPU у процесса сервера.

Клиент подключился после трёхсекундной паузы. Затем сервер ожидал данные внутри recv(). После следующей трёхсекундной паузы клиент отправил Test payload. Сервер получил строку, и обе программы завершились.

Быстрый повторный запуск сервера без SO_REUSEADDR прошёл успешно. Ошибка занятого порта не возникла.

Команда netstat -ano | findstr 9999 показала:

    TCP    127.0.0.1:9999     0.0.0.0:0          LISTENING    30176
    TCP    127.0.0.1:52566    127.0.0.1:9999     TIME_WAIT    0

После включения SO_REUSEADDR быстрый повторный запуск сервера также прошёл успешно.

## Ответы на вопросы

### 1. Почему ожидающий сервер показывает 0% CPU?

Если подключений нет, блокирующий accept() переводит поток сервера в состояние ожидания. Ядро исключает его из числа готовых к выполнению потоков, поэтому он не опрашивает очередь непрерывно и не расходует процессорное время на пустой цикл.

Когда появляется подключение, ядро пробуждает поток. Планировщик предоставляет ему процессорное время, и accept() возвращает клиентский сокет.

Показание 0% в Диспетчере задач означает отсутствие заметной процессорной нагрузки во время ожидания с учётом точности измерения.

### 2. Что показала сетевая таблица и почему соединение остаётся после завершения программы?

TIME_WAIT — состояние TCP-соединения, которое ядро некоторое время сохраняет после закрытия. Оно позволяет обработать повторную передачу завершающих сегментов и предотвращает смешивание старых пакетов с новым соединением с теми же адресами и портами.

В нашем эксперименте TIME_WAIT находился на стороне клиента: локальный адрес был 127.0.0.1:52566, а удалённый — 127.0.0.1:9999.

Серверный порт 9999 уже находился в состоянии LISTENING у нового процесса. Следовательно, ошибка занятого серверного порта в эксперименте не воспроизвелась: наличие TIME_WAIT у клиента не помешало серверу повторно выполнить bind().

### 3. Что делает SO_REUSEADDR?

Вызов:

    server_socket.setsockopt(socket.SOL_SOCKET, socket.SO_REUSEADDR, 1)

изменяет правила проверки адреса и порта при bind(). Он разрешает определённые случаи повторного использования локального адреса, которые без этого параметра могли бы быть отклонены.

Флаг не удаляет записи TIME_WAIT и не отменяет правила завершения TCP-соединения. Его точное поведение зависит от операционной системы; в Windows он также допускает некоторые случаи привязки к уже используемому адресу.

В нашем опыте сервер успешно перезапускался как без этого флага, так и с ним, поэтому устранение ошибки с его помощью продемонстрировано не было.
